可以。现在开始进入 **技术实现设计 V0.1**。这一阶段的目标不是“写代码越多越好”，而是把前面的设计翻译成一个**稳定、可扩展、能快速调试的工程骨架**。

我先给结论：

> **V0.1 最适合做成 Web 单机应用，核心引擎用 TypeScript，内容数据用 YAML/JSON，前端只负责渲染，所有游戏逻辑放在独立 Engine 层。**

这样最适合我们现在这个项目，也最方便以后接 AI。

# 四、最核心的数据：GameState

我们前面设计的所有东西，最终都汇总到这里。

我建议：

```ts
interface GameState {
  runtime: RuntimeState;
  world: WorldState;
  meta: MetaState;
}
```

## Runtime

```ts
interface RuntimeState {
  currentLocationId: string;
  currentStoryNodeId: string;

  loopId: number;

  gameTime: number;

  eventQueue: QueuedEvent[];

  currentScene?: SceneViewModel;
}
```

`gameTime` 不建议一开始用 Date。

直接用：

```text
从循环开始经过了多少分钟
```

例如：

```text
23:10 = 0
23:30 = 20
23:40 = 30
```

最容易计算。

UI再转换成人类时间。

```ts
interface WorldState {
```

例如：

```json
{

    "power_on": true,
```

第一版不要追求超级严格的复杂数据结构。

先能跑。

# 九、Condition 不要直接写 JavaScript

这个一定要提前限制。

不要内容里写：

```yaml
condition: "state.world.flags.x && time > 20"
```

短期方便，长期非常难维护。

最好结构化：

```yaml
conditions:
  all:
    - type: flag_equals
      key: warehouse_locked
      value: true

    - type: time_gte
      value: 20
```

或者：

```yaml
conditions:
  any:
    - type: memory_exists
      id: knows_knock_time

    - type: clue_discovered
      id: clue_knock
```

统一：

```text
ALL
ANY
NOT
```

这样足够覆盖绝大部分剧情需求。

# 十、ConditionEvaluator

所有系统共用同一个。

```text
Action
Event
Story Node
Clue
Memory
Scene Block
```

全部调用：

```ts
conditionEvaluator.evaluate(condition, state)
```

这是必须统一的。

否则以后你会出现：

```text
Action自己的判断逻辑
Event自己的判断逻辑
Story自己的判断逻辑
```

最后行为不一致。

这同样是核心。

```ts
applyEffects(effects, gameState)
```

足够了。

# 十二、Event Engine

核心接口可以非常简单：

```ts
eventEngine.processTrigger({
  type: "TIME_ADVANCED",
  from: 15,
  to: 20
});
```

它负责：

```text
查找候选 Event
↓
ConditionEvaluator
↓
RepeatPolicy
↓
加入 EventQueue
↓
Priority排序
↓
逐个执行
↓
EffectEngine
↓
生成 Presentation
```

# 十三、时间推进必须集中处理

不要：

```ts
state.gameTime += 5;
```

散落在代码里。

统一：

```ts
gameClock.advance(5)
```

里面负责：

```text
oldTime
↓
newTime
↓
检查 oldTime → newTime 之间所有 Scheduled Event
↓
处理Event
```

例如：

```text
当前 23:27
Action耗时5分钟
```

实际不能直接：

```text
23:32
```

因为23:30可能有 Event。

应该：

```text
23:27
↓
23:30 Event
↓
处理
↓
23:32
```

这个实现细节非常重要。

# 十四、Scene Resolver

Scene Resolver不要修改状态。

这是一个关键工程规则：

> **Resolver必须尽量是纯函数。**

输入：

```text
GameState
+
Location
+
Content
```

输出：

```text
SceneViewModel
```

例如：

```ts
interface SceneViewModel {
  locationId: string;

  title: string;

  gameTime: number;

  narrativeBlocks: string[];

  actions: ResolvedAction[];

  npcs: string[];

  exits: ResolvedExit[];
}
```

这样调试极其容易：

```text
给同一个State
↓
永远得到同一个Scene
```

不要让：

```text
resolveScene()
```

自己偷偷触发剧情。

进入场景 Event 应该由 Controller 先处理。

---

# 十五、GameController 是总调度器

UI只调用：

```ts
gameController.performAction(actionId)
```

GameController内部：

```text
validate Action
↓
ActionResolver
↓
推进Time
↓
EffectEngine
↓
EventEngine
↓
StoryResolver
↓
KnowledgeResolver
↓
如果Loop请求存在
    LoopManager
↓
SceneResolver
↓
返回新的ViewModel
```

React根本不用知道背后的东西。

---

# 十六、一次 Action 的完整事务

我建议代码思路甚至直接按照我们之前设计的“原子事务”。

```text
performAction()
```

执行：

```text
1 获取当前State Snapshot

2 再检查Action Conditions

3 开始Action Transaction

4 Time Cost

5 Action Effects

6 Event Processing

7 Knowledge Processing

8 Story Processing

9 Loop Processing

10 Resolve Scene

11 Commit State

12 写 Action/Event Log
```

以后甚至可以增加：

```text
rollback
```

用于出现异常时恢复上一State。

# 十七、内容和代码一定分离

这是这个项目能不能长期做下去的关键。

不要：

```ts
if (location === "warehouse" && time === 20) {
   ...
}
```

绝对不要。

应该：

```yaml
event:
  id: knock_event

  trigger:
    type: TIME
    at: 20

  conditions:
    ...
```

代码只知道：

> TIME Event是什么。

代码不知道：

> 仓库会敲门。

这叫 **Data-Driven**。

我们的项目非常适合这个模式。
